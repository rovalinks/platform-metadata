# Enterprise Metadata Governance Platform - Greenfield Governance

## 1. Purpose

This document defines the Greenfield governance architecture and operational model for the Enterprise Metadata Governance Platform on Google Cloud.

Greenfield governance is responsible for detecting newly created supported GCP resources, resolving their application metadata, evaluating compliance and applying required metadata through the central governance platform.

The design is:

- organisation-aware
- event-driven
- serverless
- centrally operated
- registry-driven
- capability-controlled
- auditable
- designed for near-real-time processing

The production control plane is hosted in:

```text
platform-metadata-prod
```

Development and validation are performed in:

```text
platform-metadata-dev
```

---

## 2. Greenfield Objective

The objective is to govern newly created resources without deploying remediation infrastructure into every workload project.

A resource may be created in a workload project such as:

```text
payments-dev-1
application-prod-1
shared-services-prod
```

The creation event is routed centrally to the metadata governance platform.

The governance project itself does not need to contain the workload resource.

## 4. Why Organisation-Level Routing Is Required

The governance runtime is centralised.

Creating an Eventarc trigger in `platform-metadata-prod` does not independently cause Eventarc to discover resource creation events occurring in every unrelated workload project.

The enterprise Greenfield architecture therefore uses Cloud Audit Logs plus an organisation-level Cloud Logging sink.

The organisation sink observes matching audit events from the configured organisation scope and exports them to the central Pub/Sub topic.

The path is:

```text
Resource created in workload project
             |
             v
Workload project's Cloud Audit Log
             |
             v
Organisation Logging sink
             |
             v
Central Pub/Sub topic
             |
             v
Eventarc
             |
             v
Central Cloud Run service
```

This is the key mechanism that allows a dedicated governance project to process Greenfield activity across workload projects.

---

## 5. Event Source

Greenfield processing is based on Google Cloud Audit Logs generated by resource-creation operations.

The event source is not the resource itself.

The platform processes the audit record representing the API operation that created the resource.

Relevant information can include:

- service name
- method name
- project
- resource name
- request
- response
- authentication context
- timestamp

The exact structure varies between Google Cloud services.

---

## 6. Audit Log Selection

Greenfield routing should target the audit-log category containing the validated resource-creation operation.

For many administrative resource-creation operations this is Admin Activity, but support must be confirmed per service.

A Greenfield capability must not be enabled merely because a method name appears to contain:

```text
insert
create
```

Different services use different method names and audit payload structures.

---

## 7. Organisation Logging Sink

The organisation-level Logging sink is the central Greenfield collection mechanism.

Its destination is the central Pub/Sub topic:

```text
metadata-governance-events
```

The sink filter determines which audit events enter the Greenfield pipeline.

### Design principle

The sink should be broad enough to include every validated Greenfield creation event but narrow enough to avoid unnecessary event volume.

### Do not assume one generic Compute regex solves all services

A filter such as a generic match against every Compute `*.insert` method can be useful only if every matched method has been validated by the platform.

The supported-resource/event matrix should drive the final sink filter.

---

## 8. Logging Sink Writer Identity

Cloud Logging creates a writer identity for the organisation sink.

That identity requires Pub/Sub Publisher permission on:

```text
metadata-governance-events
```

The required trust relationship is:

```text
Organisation Logging Sink
        |
        | writer identity
        | roles/pubsub.publisher
        v
metadata-governance-events
```

The writer identity must be obtained from the deployed sink.

Do not replace it with a manually assumed service-account address.

---

## 9. Pub/Sub Event Transport

The central Greenfield topic is:

```text
metadata-governance-events
```

The infrastructure also provisions the standard subscription:

```text
metadata-governance-sub
```

Pub/Sub decouples organisation-level log routing from the application runtime.

This provides:

- asynchronous event transport
- buffering
- independent producer/consumer lifecycle
- managed scalability
- delivery resilience

The platform's Pub/Sub topic must remain separate from unrelated application messaging.

---

## 10. Eventarc Trigger

The Eventarc trigger is:

```text
metadata-governance-trigger
```

The trigger listens for:

```text
google.cloud.pubsub.topic.v1.messagePublished
```

and routes matching Pub/Sub events to:

```text
Cloud Run service: metadata-governance
```

Eventarc is therefore not detecting Compute, Storage or other resources directly.

Its immediate event source in this architecture is the central Pub/Sub topic.

---

## 11. Eventarc Authentication

Eventarc delivers the event to Cloud Run using an authenticated identity.

The delivery identity requires the appropriate Eventarc receiver permissions and Cloud Run invocation permission.

The trust path is:

```text
Pub/Sub
   |
   v
Eventarc
   |
   | authenticated invocation
   v
Cloud Run
```

The governance Cloud Run service does not need anonymous public invocation for Greenfield event delivery.

---

## 12. Cloud Run Greenfield Intake

The `metadata-governance` Cloud Run service receives the Pub/Sub/Eventarc CloudEvent.

The application must first determine whether the request represents a supported Greenfield event.

Processing should fail safely for malformed or unsupported events.

A received event does not automatically mean remediation should occur.

---

## 13. Event Processing Pipeline

The logical application flow is:

```text
Receive CloudEvent
       |
       v
Decode Pub/Sub payload
       |
       v
Parse Audit Log
       |
       v
Extract serviceName / methodName
       |
       v
Classify Resource
       |
       v
Resolve Project / Resource Identity
       |
       v
Check Greenfield Capability
       |
       v
Resolve Application Registry
       |
       v
Read Current Resource Metadata
       |
       v
Evaluate Compliance
       |
       +--------------------+
       |                    |
    compliant          non-compliant
       |                    |
       v                    v
 Record outcome       Resource Adapter
                            |
                            v
                      Native GCP Update
                            |
                            v
                    Record Execution Evidence
```

---

## 14. Event Parser

The parser converts the incoming transport envelope into an internal representation of the audit event.

The parser should not contain resource-specific mutation logic.

Its responsibility is transport/audit normalisation.

Expected information includes:

```text
project_id
service_name
method_name
resource_name
request
response
timestamp
```

Not every service supplies all resource information in the same field.

---

## 15. Resource Classifier

The classifier determines the canonical platform asset type and resource identifier represented by an audit event.

For example, a classifier may map a validated Compute Engine VM creation event to the platform's Compute Instance asset type.

The classifier must be service-aware.

It should not rely solely on string matching against a generic `insert` suffix.

---

## 16. Greenfield Capability Gate

After classification, the platform checks whether that resource type is explicitly enabled for Greenfield governance.

This distinction is critical:

```text
Client exists
    !=
Brownfield supported
    !=
Greenfield supported
```

A resource can have a client/adapter in the repository but still be disabled for Greenfield because its creation event has not been validated.

---

## 17. Greenfield Support Requirements

A resource type should be marked Greenfield-supported only after all of the following are verified:

```text
[ ] Exact resource creation operation identified
[ ] Audit log category confirmed
[ ] serviceName confirmed
[ ] methodName confirmed
[ ] Organisation sink filter matches event
[ ] Event reaches central Pub/Sub
[ ] Eventarc delivers event
[ ] Parser handles payload
[ ] Classifier identifies asset correctly
[ ] Project ID resolves correctly
[ ] Resource name resolves correctly
[ ] Capability explicitly enables Greenfield
[ ] Registry binding resolves
[ ] Adapter reads current metadata
[ ] Required IAM is available
[ ] Metadata mutation succeeds
[ ] Duplicate event delivery is safe
[ ] Failure/retry behaviour is safe
[ ] BigQuery execution evidence is written
```

Until these conditions are met, the resource must not be advertised as Greenfield-supported.

---

## 18. Application Registry Resolution

Greenfield does not hardcode application metadata into event handlers.

Once the project is identified, the platform resolves the corresponding application through the Application Registry.

The registry can provide governance values such as:

- application/product
- team
- owner
- budget owner
- organisation
- department
- cost centre
- environment
- region
- business criticality

If the workload project has no valid registry binding, the event must be handled according to the platform's defined unsupported/unbound-project policy rather than inventing metadata.

---

## 19. Compliance Evaluation

After registry resolution, the platform reads the resource's current metadata.

Required governance metadata is compared with actual metadata.

The resource can then be classified as:

```text
COMPLIANT
NON_COMPLIANT
UNSUPPORTED
UNBOUND
FAILED
```

The exact internal status names may vary by implementation, but the behaviour must remain explicit and auditable.

Already compliant resources should not receive unnecessary update calls.

---

## 20. Resource Adapter

The service-specific adapter performs the actual resource metadata operation.

Adapters isolate differences between Google Cloud APIs.

Examples of service-specific differences include:

- label fingerprints
- ETags
- regional versus zonal resource names
- project-level resources
- asynchronous operations
- different update-mask semantics
- different metadata APIs

The Greenfield handler should dispatch to the adapter rather than implementing service mutation directly.

---

## 21. Metadata Preservation

Where supported by the platform policy, existing unrelated resource labels must be preserved.

The governance platform should reconcile managed governance keys rather than replacing all resource labels indiscriminately.

The application configuration includes the control:

```text
PRESERVE_EXISTING_LABELS
```

This behaviour must be validated for every adapter because Google Cloud update semantics differ by service.

---

## 22. IAM Requirements

Greenfield processing requires several separate IAM paths.

### Organisation sink

```text
Logging sink writer
    -> Pub/Sub Publisher
```

### Eventarc

```text
Eventarc delivery identity
    -> Eventarc event receiver
    -> Cloud Run Invoker
```

### Governance runtime

```text
Runtime service account
    -> Registry read
    -> BigQuery evidence access
    -> Resource read
    -> Enabled resource mutation
```

The runtime mutation permissions are governed by the active supported-resource capability set.

See `IAM.md` for the detailed permission model.

---

## 23. BigQuery Greenfield Evidence

Greenfield execution results are persisted in the governance BigQuery model.

The primary execution evidence table is:

```text
remediation_execution
```

Relevant fields include:

```text
execution_id
run_id
project_id
asset_type
resource_name
managed_labels
status
error_message
executed_at
execution_mode
service_name
method_name
duration_ms
```

Greenfield activity should be identifiable through:

```text
execution_mode = GREENFIELD
```

This allows Greenfield operational reporting to remain separate from Brownfield batch execution.

---

## 24. Dashboard Greenfield Reporting

The dashboard/reporting layer should derive Greenfield metrics from operational data rather than repository snapshots or static configuration.

Useful Greenfield reporting includes:

- total Greenfield events
- successful remediation
- failed remediation
- unsupported events
- recent Greenfield activity
- project distribution
- resource-type distribution
- service/method distribution
- execution duration
- recent failures

The dashboard must not present repository capability definitions as if they were live execution counts.

---

## 25. Idempotency

Event-driven systems must assume duplicate delivery is possible.

A repeated creation event must not cause destructive or incorrect metadata behaviour.

The processing model should be naturally idempotent:

```text
Read current metadata
      |
      v
Evaluate required metadata
      |
      +-- already correct -> no unnecessary mutation
      |
      +-- missing/incorrect -> reconcile managed metadata
```

Adapters must preserve safe retry behaviour.

---

## 26. Resource Availability Timing

An audit event can arrive before every downstream resource API read is immediately consistent.

The platform must handle temporary resource lookup failures safely.

Where the implementation uses retry handling for transient `404` behaviour, the retry must remain bounded.

A temporary lookup failure should not be treated as proof that the resource is permanently unsupported.

---

## 27. Failure Handling

Failures should be classified rather than silently ignored.

Typical failure categories include:

```text
EVENT_PARSE_FAILURE
UNSUPPORTED_SERVICE
UNSUPPORTED_METHOD
UNSUPPORTED_RESOURCE
PROJECT_NOT_BOUND
RESOURCE_LOOKUP_FAILURE
IAM_DENIED
REGISTRY_FAILURE
COMPLIANCE_FAILURE
REMEDIATION_FAILURE
BIGQUERY_WRITE_FAILURE
```

The exact implementation status vocabulary may differ, but logs must contain enough context to diagnose the stage that failed.

---

## 28. Greenfield Logging

Operational logs should include useful structured context such as:

```text
execution_mode
project_id
asset_type
resource_name
service_name
method_name
status
duration
error
```

Sensitive data from audit requests should not be copied unnecessarily into application logs.

Logging should support correlation from:

```text
Audit event
 -> Cloud Run execution
 -> Resource remediation
 -> BigQuery evidence
```

## 29. Greenfield End-to-End Test

A valid test must create a supported resource in a governed workload project.

Example test pattern:

```text
1. Select a registered DEV workload project
2. Confirm the resource type is Greenfield-enabled
3. Create the resource in that workload project
4. Confirm Admin Activity audit event
5. Confirm exact serviceName/methodName
6. Confirm organisation sink filter matches
7. Confirm central Pub/Sub receives event
8. Confirm Eventarc delivery
9. Confirm Cloud Run receives event
10. Confirm classifier output
11. Confirm registry resolution
12. Confirm metadata update
13. Confirm BigQuery GREENFIELD evidence
14. Confirm dashboard/reporting update
```

Creating the resource only in `platform-metadata-dev` is not sufficient to prove organisation-level routing from workload projects.

## 30. Diagnostic Sequence When Nothing Triggers

When a workload resource is created but there are no governance logs, troubleshoot from the source forward.

```text
Resource
  |
  v
Audit Log?
  |
  v
Sink filter match?
  |
  v
Pub/Sub message?
  |
  v
Eventarc delivery?
  |
  v
Cloud Run request?
  |
  v
Parser/classifier?
  |
  v
Capability?
  |
  v
Registry?
  |
  v
Adapter?
```

Do not begin by changing application code if the audit event never reached Cloud Run.

---

## 31. Audit Log Verification

First verify that Google Cloud generated the expected audit event in the workload project.

Check:

```text
protoPayload.serviceName
protoPayload.methodName
resource/project
timestamp
```

The observed event is the source of truth for building the Greenfield filter/classifier.

Do not infer a method name solely from the corresponding REST API method name.

---

## 32. Sink Filter Verification

If the audit event exists but the platform receives nothing, determine whether the organisation sink filter actually matches that exact event.

Check:

- log name/category
- service name
- method name
- excluded projects
- organisation sink scope
- destination topic

A syntactically valid filter can still be logically wrong.

---

## 33. Pub/Sub Verification

If the sink matches but Cloud Run receives nothing, verify the central topic.

Confirm:

- topic exists
- sink destination is correct
- sink writer has Pub/Sub Publisher
- messages are being published
- no incorrect project/topic is referenced

The standard subscription can be useful for controlled troubleshooting, but consuming diagnostic messages must be done carefully because subscription semantics differ from Eventarc's managed subscription.

---

## 34. Eventarc Verification

Confirm:

- trigger exists
- trigger region is correct
- event type is `google.cloud.pubsub.topic.v1.messagePublished`
- source topic is correct
- destination service is correct
- destination region is correct
- trigger identity is correct
- trigger identity can invoke Cloud Run

A trigger in ACTIVE state proves configuration health, not that the organisation sink is sending matching events.

---

## 35. Cloud Run Verification

If Eventarc delivery occurs, inspect Cloud Run logs.

Determine whether:

- request reached the service
- Pub/Sub payload decoded
- Audit Log parsed
- classifier recognised service/method
- project resolved
- capability accepted/rejected event
- registry resolved
- adapter executed
- BigQuery write succeeded

This isolates transport problems from application problems.

---

## 36. Resource Onboarding Process

Every new Greenfield resource type should follow a controlled onboarding process.

```text
Phase 1 - Research
    Identify official creation API and Audit Log behaviour

Phase 2 - Capture
    Create test resource and capture real audit event

Phase 3 - Classifier
    Add/validate event classification

Phase 4 - Capability
    Explicitly enable Greenfield capability

Phase 5 - Adapter
    Validate metadata read/update

Phase 6 - IAM
    Add only required permissions

Phase 7 - DEV
    Execute end-to-end test

Phase 8 - Evidence
    Verify BigQuery and dashboard

Phase 9 - Production
    Promote capability after approval
```

This prevents partially implemented integrations from entering production.

---

## 37. Greenfield and Brownfield Relationship

Greenfield and Brownfield should not have separate metadata standards.

They use the same:

- Application Registry
- required metadata
- capability model
- resource adapters where applicable
- compliance principles
- audit/reporting platform

Only the ingestion/orchestration path differs.

```text
Brownfield -> Cloud Asset Inventory
Greenfield -> Audit Event

Both -> Registry -> Capability -> Compliance -> Adapter -> Evidence
```

---

## 38. Exclusions

The platform must support exclusions for resources/projects that must not be governed by the normal remediation path.

Examples include:

- governance control-plane projects
- platform-owned registry buckets
- explicitly excluded projects
- explicitly excluded resources

Exclusions must be configuration-driven.

They must not be implemented by scattering hardcoded project/resource names through resource adapters.

Recommended Greenfield operational metrics include:

- events classified

- registry resolution failures
- compliant resources

## 42. Cost Characteristics

Greenfield governance is event-driven.

There is no need for a permanently running polling VM or worker fleet.

Primary variable-cost components include:

- Cloud Logging routing/volume
- Pub/Sub
- Eventarc
- Cloud Run execution
- BigQuery storage/querying
- target API activity where applicable

Cloud Run is configured to support scale-to-zero, providing zero idle application instance infrastructure when no minimum instance is configured.

Actual production cost should be measured from observed event volume and execution telemetry.

## 43. Greenfield Security Controls

Production Greenfield should maintain:

```text
[ ] Dedicated PROD governance project
[ ] Dedicated PROD runtime identity
[ ] Authenticated Eventarc -> Cloud Run invocation
[ ] No anonymous Cloud Run requirement
[ ] Logging sink publisher restricted to central topic
[ ] Least-privilege resource mutation role
[ ] Registry read control
[ ] BigQuery governance-data access control
[ ] Configuration-driven exclusions
[ ] Auditable execution evidence
```

---

## 44. Anti-Patterns

Do not:

- create one Eventarc trigger and assume it automatically sees every project
- test only by creating resources in the governance project
- use a generic `.*insert` filter without validating matched resource types
- assume REST method names exactly match Audit Log method names
- enable Greenfield because an adapter exists
- hardcode workload project IDs in classifiers
- hardcode application metadata in event handlers
- grant broad Editor/Owner roles to solve adapter failures
- replace all existing labels when only managed labels need reconciliation
- assume events are delivered exactly once
- treat a temporary resource `404` as permanent failure without validated retry behaviour
- use repository snapshot data as live Greenfield dashboard metrics
- mix DEV and PROD event infrastructure

## 46. Architecture Summary

The Greenfield architecture provides central, event-driven metadata governance across the GCP organisation.

The key processing path is:

```text
Workload Resource Creation
        |
        v
Cloud Audit Logs
        |
        v
Organisation Logging Sink
        |
        v
Central Pub/Sub
        |
        v
Eventarc
        |
        v
Cloud Run
        |
        v
Parser / Classifier
        |
        v
Capability Gate
        |
        v
Application Registry
        |
        v
Compliance
        |
        v
Resource Adapter
        |
        v
Native GCP API
        |
        v
BigQuery Evidence
```

This design centralises governance without requiring an always-running polling system or a separate governance agent in every workload project.

Greenfield support remains explicit and capability-controlled so that only fully validated resource types are enabled in production.
